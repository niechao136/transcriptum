# 医疗平台 · 系统架构设计

> 依据 `醫療平台原型.html`（原型 v2）拆解，结合已验收的 MOSS 推理服务现状设计。
> 原型是「目标形态」，本文是**全新系统**的设计蓝本，不继承旧 Transcriptum 的架构约束。

- 版本：1.0
- 日期：2026-11-25
- 输入证据：`醫療平台原型.html`（1218 行，13 个视图）、`docs/MOSS部署验收报告.md`、`docs/Transcriptum公网访问部署说明.md`

---

## 一、先说结论：这个系统的三个本质

读完原型，它不是「录音转文字工具」，而是**医院内部的知识生产与治理平台**。三个特征决定了架构：

1. **权限是双维度的**：角色决定「能做什么」（6 个能力位），组织绑定决定「能碰哪些单位」（树形继承）。两者相乘，且必须在服务端逐请求判定。原型里每个视图都在做 `isSys / inScope / can` 三连判断 —— 这不是 UI 装饰，是安全边界。

2. **会议记录的核心资产不是文字，是「依据链」**。原型 `M1_GEN` 把每个生成项绑定到 `{seg, key}`：句子 0 必须仍含「跌倒」，否则重新生成时该结论自动消失。这是**可溯源到逐字稿的结论**，比普通摘要严格得多，也直接决定了数据模型必须显式存这条链。

3. **推理必须本地化**。音频不出内网是硬约束，MOSS 已在本机 WSL2 上以 RTF 0.197 跑通。推理层是独立服务，不是应用进程里的库。

### 2.2 角色与能力位

```
ROLE = { sys: 系统管理员, mgr: 管理者, user: 一般用户 }

CAP = {
  orgTree:      { sys },
  kbManage:     { sys, mgr },
  settings:     { sys, mgr },
  formTplManage:{ sys, mgr },
  audit:        { sys, mgr },
  accounts:     { sys, mgr },
}
```

**关键约束**（原型已实现，必须保留）：

- `canManageUser`：管理者只能管**自己范围内**的 `user`，不能管 `mgr` 或其他 `mgr`；不能管自己。
- `canResetPw`：sys 可重设任何人（含自己）；mgr 只能重设自己管得到的人。
- `activeSysCount()`：至少保留一位启用中的 sys，否则拒绝停用。
- 权限变更 / 绑定变更 → `ver += 1` → **强制登出**该账号。

### 2.3 组织与权限模型

```
scopeNodes(u) = sys ? 全部节点 : ∪ subtree(b) for b in u.bind
inScope(u, node) = node ∈ scopeNodes(u)
resolveSetting(kind, node) = 沿 pathToRoot(node) 找第一个有值的节点
```

三个必须照抄的语义：

1. **绑定即继承**：绑定到 `NUR` 自动获得 `NUR` 全部下层的范围。
2. **搬移不追溯登录**：节点搬移后，绑定新上层的人立即获得权限、绑定旧上层的人失去，**但都不强制登出**，下次操作按新结构判断。
3. **设定向上继承**：`settings`（RAG prompt / rerank / 阈值）与 `tpl`（纪要字段）都是「本节点有值就用，否则向上取」。

### 2.4 会议生命周期状态机

```
上传/录音 → 排隊中 → 處理中 → 草稿 → (定稿) → 已定稿
                        ↓
                      失敗（可重试）
```

原型状态值共 5 个：`排隊中 / 處理中 / 草稿 / 已定稿 / 失敗`。

**保留期规则**（易错，必须精确）：

- 录音：**第一次定稿**起算 `retentionDays`（默认 90 天）；未定稿前不开始计时。
- 逐字稿与会议记录：**永久保存**，录音删除后仍保留。
- 修改 `retentionDays` **回溯套用到所有既有记录**。
- 到期日按**服务器操作系统时区**计算。

### 2.5 会议详情页的能力（最复杂的一屏）

| 能力 | 原型实现要点 |
|---|---|
| 播放跳转 | `data-seek` 按句跳播，`playFrom(m, sec)` |
| 逐字稿编辑 | `SEDIT` 逐句编辑模式 |
| 说话人绑定 | `resolveSid` + 声纹自动标注；未注册显示 `S1..Sn` |
| AI 修正建议 | 句级 `hint.fix`，可「采用」或「忽略」，两者都留审计 |
| 纪要生成 | `genMinutes`，字段来自 `tpl`，每项带 `{seg, key}` 依据 |
| 依据校验 | `key` 不在该段文字里 → 该项不出现在重新生成的纪要 |
| 定稿 | 确认框；首次定稿写 `firstFinal` 并提示录音保留到期日 |
| 修改已定稿 | 仍可改，但改动进审计 |

### 2.6 检索与问答

```
searchable(u) = { m | m.status == '已定稿' ∧ m.minutes ≠ null ∧ inScope(u, m.unit) }
```

**只搜已定稿**，草稿与逐字稿不参与。问答规则（原型明写的产品约束）：

- 按关键词命中纪要字段 → 返回**最多 4 条**带出处的答案；
- 命中不到 → 明确回答「查无足以回答这个问题的内容」，**不得用自己的知识推测**；
- 答案在**提问当下生成**，之后不追溯修改或撤下（快照语义）。

### 2.7 知识库（卫教 RAG）

| 语义 | 原型实现 |
|---|---|
| 可见范围 | `kbRight`：本节点及下层 = `manage`；本节点的**祖先**（`pathToRoot(b).slice(1)`）= `view`；否则无权 |
| 分块 | 每份素材预切 `chunks[]`，带 `topic` |
| 设定继承 | `settings.rag[node]` 的 `prompt / rerank / threshold` 按树继承 |
| 重新处理 | 同一份素材原地重跑，**不新增副本**；可替换原档 |
| 审核态 | `st: 允许存取` 等，未审核不参与检索 |

> 注意知识库与会议记录**共享方向相反**：知识库可往下共享（祖先看得到下层的），会议记录**不往下共享**（只能在绑定范围内看）。

### 2.8 表单模块

- 模板按单位维护，**可被下层单位使用**（`上層共享` 标记）；
- 填写结果**归属填写时所在单位**，不绑定病人身份；
- 编辑权：`canEditRecord(u, unit, by)` —— sys 全通，mgr 限范围内，user 只能改自己填的。

### 2.9 审计（不可篡改）

记录：登录（**含被拒**）、新增、修改、删除、权限调整、强制登出。
**不记录检视**。日志不可改不可删。
可见范围：sys 全见；mgr 见「关联单位在范围内」或「操作者目前在范围内」的记录。

### 2.10 声纹

- **自愿注册，只有本人能注册/删除**；
- 仅院内保存与比对；
- 删除或停用后，**新处理的录音**不再自动对应，**已定稿纪录不变**（不可追溯修改历史）。

## 三、系统架构

> 📊 可交互架构图：[医疗平台-系统架构.html](architecture/医疗平台-系统架构.html)
> 会议处理时序图：[医疗平台-会议处理时序.html](architecture/医疗平台-会议处理时序.html)

### 3.1 分层总览

```
┌──────────────────────────────────────────────────────────────┐
│ 接入层    Nginx / HTTPS 终止 / 静态资源 / 反向代理              │
├──────────────────────────────────────────────────────────────┤
│ 前端      React SPA（13 视图）                                │
│           权限只做「显示与否」，真正的判定在服务端               │
├──────────────────────────────────────────────────────────────┤
│ API 层    FastAPI · 统一鉴权中间件 · 请求上下文(user, scope)     │
│           路由按领域拆分，全部先过权限判定                       │
├──────────────────────────────────────────────────────────────┤
│ 领域层    会议 · 组织权限 · 知识库 · 表单 · 检索问答 · 审计      │
│           纯业务规则，不碰 IO                                   │
├──────────────────────────────────────────────────────────────┤
│ 任务层    队列 + Worker  · 转写/校对/纪要/知识库索引            │
│           状态机、重试、进度、失败通知                           │
├──────────────────────────────────────────────────────────────┤
│ 推理层    MOSS ASR（vLLM，本地 GPU）· LLM（纪要/校对/RAG）      │
│           独立进程，HTTP 调用，音频不出内网                      │
├──────────────────────────────────────────────────────────────┤
│ 存储层    PostgreSQL(+pgvector) · MinIO(音频/原始档) · Redis    │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 为什么这样分层（每条都对应原型的硬需求）

| 决策 | 依据 |
|---|---|
| 权限判定放**服务端中间件 + 领域层双重** | 原型里每个视图都在算 `scope`；UI 隐藏按钮不算数，接口必须自己判 |
| 推理**独立服务**而非进程内 | 音频不出内网 + 已验收的 vLLM 部署形态；应用扩容不应拖着 GPU |
| 任务**异步 + 状态机** | 42 分钟音频转写是分钟级任务，必须能排队、能失败重试、能通知 |
| 会议记录用**句子时间轴** | 逐句跳播、逐句校对、依据链都锚在 `seg` 上 |
| 结论存**依据链** `(seg_id, key)` | 原型 `M1_GEN` 的核心；重新生成时依据没了结论就该消失 |
| 审计**只增不改** | 原型明写「稽核纪录不能修改或删除」 |
| 向量检索用 **pgvector** | 知识库与会议纪要都要检索，且需要与业务表同库做范围过滤 |

### 3.3 一次会议从上传到定稿的完整链路

```
1. 上传      前端 → POST /meetings（multipart）
             校验格式/大小 → 落 MinIO → 建 meeting(status=排隊中) → 入队
             注意：读不到时长也要先收下，背景再判定失败（原型 SAMPLES.bad 语义）

2. 转写      Worker 取任务 → 归一化 16k mono → 调 MOSS /v1/audio/transcriptions
             → 解析 [start][Sxx]text[end] → 写 segment + speaker_cluster
             → status=處理中

3. 声纹对齐  已注册声纹的账号 → 自动标注姓名；未注册 → S1..Sn
             低置信/歧义 → 标记待人工确认

4. 校对      LLM 逐句保守纠错 → ai_edits（结构化 from→to）+ hint
             前端逐句确认/编辑/驳回

5. 纪要生成  按 resolveSetting('tpl') 取字段 → LLM 生成
             每个生成项必须绑定 (seg_id, key) 才落库

6. 定稿      status=已定稿，写 first_final_at
             录音保留期从此刻起算
             进入 searchable 集合

7. 检索      仅已定稿 + inScope → 关键词 + 向量 → 带出处返回
```

### 3.4 状态机（详细）

```
queued ──claim──> processing ──ok──> draft ──finalize──> finalized
   │                  │
   │                  └──fail──> failed ──retry──> queued
   └──cancel──> cancelled
```

`failed` 保留 `error_msg` 与已完成的中间产物（已转出的句子不丢），重试从失败阶段续跑。

## 四、模块设计

### 4.1 模块边界

| 模块 | 职责 | 不做什么 |
|---|---|---|
| `auth` | 登录、密码、会话版本(`ver`)、强制登出 | 不做业务权限判定 |
| `org` | 组织树 CRUD、搬移、删除守卫、绑定 | 不做业务数据过滤 |
| `rbac` | `scopeNodes / inScope / can / canManageUser / canEditRecord / kbRight` | 不碰数据库以外的缓存一致性 |
| `meeting` | 会议 CRUD、上传、状态机、定稿 | 不做推理 |
| `transcript` | 句子时间轴、逐句编辑、说话人绑定、声纹对齐 | 不生成纪要 |
| `minutes` | 纪要字段生成、依据链校验 | 不做 ASR |
| `rag` | 知识库 CRUD、分块、索引、重新处理 | 不负责问答措辞 |
| `qa` | 检索、有据回答、快照 | 不编造内容 |
| `forms` | 模板、填写、结果归属 | 不绑定病人 |
| `audit` | 只增日志、范围过滤查询 | 不允许改删 |
| `notify` | 站内通知、事件订阅 | 第一版不做外送 |
| `task` | 队列、worker、重试、进度 | 不含业务规则 |

### 4.2 统一鉴权上下文

每个请求在进入领域层前构造：

```python
@dataclass(frozen=True)
class Ctx:
    user_id: str
    role: Literal["sys", "mgr", "user"]
    bind: tuple[str, ...]        # 绑定节点
    scope: frozenset[str]        # 预计算的可见节点（含子树）
    ver: int                     # 会话版本，权限变更即失效
```

`scope` 在登录时算好放进会话；`ver` 变化（权限/绑定调整）时**该用户所有在途请求一律 401**，实现「强制登出」。这样避免每个请求都递归遍历组织树。

### 4.3 依据链模型（本系统最独特的部分）

```python
@dataclass
class MinutesItem:
    field_key: str          # 如 '討論重點'
    text: str
    seg_id: int             # 依据所在句子
    key: str                # 该句必须仍包含的关键词
```

**重新生成规则**（照抄原型语义）：

```python
def regenerate(m):
    items = []
    for it in m.existing_items:
        seg = load_segment(it.seg_id)
        if it.key not in seg.text:      # 依据被删改
            continue                     # 结论自动消失
        items.append(it)
    return items
```

这条规则是产品灵魂：**没有依据的结论不该存在**。

#### 三个特殊字段的例外（原型硬编码，别漏）

`genMinutes` 里有三个字段不走依据链：

| 字段 | 来源 | 说明 |
|---|---|---|
| 出席人員 | `m.segs` 的说话人去重 | 未识别出人时填「未提及」 |
| 會議名稱 | 上传时的 `m.title` | 直接取元数据 |
| 日期 | `m.date` | 直接取元数据 |

其余字段一律走「(seg, key) 依据链」：`segments[seg_id].text` 必须**仍包含** `key`，
否则该结论在重新生成时消失。`{who}` 占位符替换为该句的说话人名。

## 五、数据模型

### 5.1 核心表

```sql
-- 组织
org_node(id, parent_id, name, type, sort)                    -- 类型可自定义
user(id, name, role, password_hash, must_change, disabled,
     voiceprint_ref, ver, created_at)
user_bind(user_id, node_id)          -- 多对多，至少一个

-- 会议
meeting(id, unit_id, title, date, duration_ms, uploader_id,
        status, audio_ref, first_final_at, template_snapshot,
        error_msg, created_at)
segment(id, meeting_id, seq, start_ms, end_ms,
        text, raw_text, speaker_id, low_confidence,
        lang, orig_text,                  -- 台语段落：lang='台'，orig_text 存原话
        edited_by, edited_at)
speaker_cluster(id, meeting_id, label, person_id, needs_review, confidence)
minutes_item(id, meeting_id, field_key, text,
             seg_id, key, source)      -- ★ 依据链
meeting_field(id, meeting_id, field_key, value)   -- 纪要原文

-- 知识库
kb_doc(id, unit_id, name, kind, status, topic, original_ref, uploaded_by)
kb_chunk(id, doc_id, seq, text, embedding vector(1024))

-- 表单
form_tpl(id, unit_id, name, fields jsonb, status, created_by)
form_result(id, tpl_id, unit_id, filled_by, values jsonb, at)

-- 系统
setting(kind, node_id, value jsonb)   -- rag / tpl / retentionDays
audit_log(id, at, actor_id, op, target, units jsonb)  -- 只增
notification(id, user_id, kind, text, link, read, at)
retention_policy(days)                -- sys 可改，回溯套用
```

### 5.2 索引与约束要点

- `segment(meeting_id, seq)` 唯一；`text` 可改但 `raw_text` 不可变（审计对照）。
- `minutes_item` 外键指向 `segment`，句子被删则级联删结论（保持依据链闭合）。
- `audit_log` 加 `REVOKE UPDATE, DELETE`，从数据库权限层保证不可篡改。
- `kb_chunk.embedding` 建 HNSW 索引；检索时**先按 `unit_id ∈ scope` 过滤再排序**，绝不先全局检索再过滤。
- `meeting.unit_id` 建索引（范围查询高频）。

## 六、接口设计（按领域）

统一前缀 `/api`，统一错误体 `{code, message, detail}`。

### 6.1 认证
```
POST /auth/login              → {token, user, must_change}
POST /auth/change-password
POST /auth/logout
```

### 6.2 会议
```
POST   /meetings                      上传（multipart）
POST   /meetings/{id}/jobs            重试/重新处理
GET    /meetings?unit=&status=&q=     列表（服务端按 scope 过滤）
GET    /meetings/{id}                 详情（含 segments + minutes）
PATCH  /meetings/{id}                 改标题/日期
POST   /meetings/{id}/finalize        定稿
GET    /meetings/{id}/audio           Range 播放
PATCH  /segments/{id}                 逐句编辑/说话人绑定
```

### 6.3 纪要
```
POST /meetings/{id}/minutes/generate
GET  /meetings/{id}/minutes
PATCH /minutes/items/{id}             人工修正（保留 seg/key）
```

### 6.4 检索问答
```
GET  /search?q=&range=this_month|last_month
POST /qa      {question} → [{date,title,field,text,cite}]
```
服务端强制：`status='已定稿' ∧ unit ∈ scope`；无命中返回固定拒绝文案。

### 6.5 知识库

## 七、非功能设计

### 7.1 安全

| 项 | 设计 |
|---|---|
| 传输 | 公网 HTTPS（已具备），内部服务间 mTLS 可选 |
| 权限 | 服务端强制；前端隐藏不算数 |
| 会话 | 权限/绑定变更 `ver+1` → 全端强制登出 |
| 密码 | bcrypt；首次登录强制改密 |
| 音频 | 只在本机 MinIO；推理走内网 HTTP；**不出公网** |
| 审计 | 表级禁改删；记录登录失败 |
| 声纹 | 本人可删；删后不追溯历史 |

### 7.2 性能（有实测依据）

- MOSS 实测 **RTF 0.197**（19 秒音频 / 3.75 秒耗时，来源 `docs/MOSS部署验收报告.md`）。
  42 分钟音频按此外推约 8.3 分钟——**外推值未经实测**，长音频的 RTF 可能因
  attention 与 token 上限而恶化，上线前必须用真实长会议复测。
- 单 GPU 串行转写 → 队列必须按 FIFO + 可见进度；多 GPU 时按 `meeting.unit` 分片。
- 检索走 pgvector HNSW + 范围过滤，避免全表扫。

### 7.3 可靠性

- 任务失败保留中间产物，重试从失败阶段续跑。
- 转写幂等：同一 `meeting_id + stage` 重复执行覆盖而非追加。
- 录音删除只删 `audio_ref`，`segment` 与 `minutes_item` 永久保留。

### 7.4 可观测

- 结构化日志带 `trace_id / meeting_id / user_id`。
- 任务指标：排队时长、转写时长、失败率、RTF。
- 推理层独立健康检查，队列在推理不可用时暂停取任务（避免批量失败）。

## 八、与原型的一致性检查表

| 原型行为 | 架构落点 | 风险 |
|---|---|---|
| `inScope` 继承子树 | `rbac.scope` 登录时预计算 | 组织搬移后需清相关用户 scope 缓存 |
| 权限变更强制登出 | `user.ver` | 需在中间件比对会话 ver |
| 会议不往下共享 | `meeting.unit_id` 精确匹配 scope | 与知识库共享方向相反，勿写反 |
| 只搜已定稿 | `qa/searchable` 固定条件 | 草稿泄漏是重大事故 |
| 依据链 `seg+key` | `minutes_item` 表 | 句子删除需级联 |
| 录音保留期从首次定稿算 | `first_final_at` + `retention_days` | 未定稿不计时 |
| 改保留期回溯 | 到期日**动态计算**，不落库 | 若落库则无法回溯 |
| 审计不记录检视 | 只在写操作埋点 | 误记会让日志膨胀且语义错误 |
| 知识库祖先可 view | `kbRight` 单独实现 | 不能用 `inScope` 代替 |
| 表单结果归属单位 | `form_result.unit_id` | 绑定填写时单位而非用户 |

## 十、必须由团队决策的开放问题

这些问题原型没给答案，**不要替产品拍板**：

1. **台语识别质量**：原型已定交互（见 §2.5）：台语段落正文显示华语译文，原话折叠在下方
   「台語原話：…」，句子标 `lang='台'` 并显示「台語→華語」徽标。**格式已定，待验证的是
   MOSS 对台语的实际识别率**——这决定是否需要额外的台语转写模型或人工补录流程。
2. **声纹比对阈值**：误标说话人比不标更糟，阈值与人工确认策略需产品定。
3. **单个音频上限**：原型有 520MB WAV 样例，是否设上限、是否分段转写？（MOSS 长音频 token 上限是真实约束）
4. **并发与 GPU 数**：单卡串行是否可接受？高峰期排队多久算不可接受？
5. **审计保留期**：审计「永久」是否与个资法冲突？需法务确认。
6. **表单模块**：原型明写「介面细节尚待定义」，本设计只保留骨架，不做详细设计。
